AgentTracker — Discussion Notes
Date: October 14, 2026

This document summarizes the discussion so far. It records the project goals
and proposed design; it is not a verbatim transcript. Implementation choices
remain open unless explicitly stated below.

1. PROJECT PURPOSE

Build a tracker that follows an AI agent during its runtime. A user launches
the agent and can see in real time where it is working within the system or
file structure and what it is doing.

For example, if an agent creates files in a directory, the tracker should
show that activity in that directory. When the agent is idle, the tracker
should report its current or last known location.

File modification is only one example. Tracking must also include commands
run by the agent and other observable activities.

All project files are to be kept in:
/projects/standard/support/shared/lamx0031/Codex/AgentTracker

A README.md has been created with the project overview, intended behavior,
examples, initial scope, and planning status.

2. FILESYSTEM MAP

The initial idea is to use the tree command to generate a detailed map of
the project's directories and individual files. This map will provide the
visual structure on which the agent's activity can be located.

The map should include file dates, particularly modification times, to help
detect changes. Proposed metadata for each entry includes:

- Path.
- Entry type: file or directory.
- Modification time, with sufficient precision for rapid changes.
- File size as another change signal.

The tree command is useful for displaying the structure. A structured
filesystem scan was proposed for the tracker's internal representation,
making paths and metadata easier to query and update before rendering them
as a tree. This implementation choice has not yet been finalized.

Hidden files and exclusions should be configurable. Large directories such
as .git and dependency directories can make a full tree expensive and hard
to navigate.

3. MAP UPDATES AND ATTRIBUTION

A proposed sequence is:

1) Scan the project directory to establish a baseline map.
2) Track file creation, modification, deletion, and movement to update it.
3) Connect agent activity events to attribute actions and display runtime
   state and working locations.

Filesystem notifications were proposed for live updates, with periodic
scans to catch missed changes.

Modification times can indicate that a file changed, but cannot identify
who changed it. Users, other agents, and background processes may also
change files. Filesystem changes alone also do not reveal reading, command
execution, or model processing.

Until a change can be attributed to an agent, the display should describe it
as a filesystem change detected rather than a confirmed agent action.

4. AGENT ACTIVITY MODEL

The user clarified that the design should first lay out expected agent
behavior, then use that model to track activity and location. Commands and
other actions are part of this model, beyond file modifications.

Each activity should describe:

- Who is acting.
- What the agent is doing.
- Where the action is happening.
- Whether the action is running or has finished.

Proposed behavior categories and display rules:

Agent starts:
  Show "Starting session" at its initial working directory.

Lists or searches files:
  Show "Exploring" or "Searching" at the directory being searched.
  Include matching files when known.

Reads a file:
  Show "Reading" at the file path.

Creates, edits, moves, or deletes files:
  Show the corresponding operation at the affected paths.

Runs a command:
  Show the command and running status at its working directory.
  Include known target paths.

Runs tests or a build:
  Show "Testing" or "Building" when the action can be identified.
  Include its working directory and known targets.

Calls an external tool or service:
  Show the tool name, operation, and external resource.
  Retain the local working directory as context.

Performs a model step:
  Show "Processing" when reported by the runtime.
  Retain the last known working location.

Waits for input or approval:
  Show "Waiting for user" at the last known working location.

Becomes idle:
  Show "Idle" and retain the last known working location.

Finishes or stops:
  Show "Completed", "Cancelled", or "Failed", with the final known
  location.

5. WHAT LOCATION MEANS

The proposed model separates two concepts:

- Working directory: the execution context where an action runs.
- Target resources: the files, directories, or external resources involved
  in the action.

For example, a command launched from /project may read
/project/src/main.py and write into /project/output. The tracker should
retain /project as the execution context and highlight the affected paths
when they are known.

External activity may not have a meaningful position in the local file
tree. The tracker should identify the external resource while retaining
the local context.

6. PROPOSED ACTIVITY RECORD

Identity:
  Agent ID, session ID, and activity ID.

Action:
  Activity type, tool name, and command or operation details.

Location:
  Working directory and known target paths or external resources.

Lifecycle:
  Start time, end time, status (running, completed, failed, or cancelled),
  and result information such as an exit code.

Evidence:
  Whether the information comes directly from an agent tool event,
  process observation, or an inference.

7. OBSERVABILITY RULES

The display should distinguish observed information from inferred behavior.
For example, a command event can establish that the agent is running
"python script.py", but the command text alone does not establish every
file the script accesses.

Silence should mean "No recent activity observed" unless the runtime
confirms that the agent is idle. A lack of filesystem changes does not
establish idleness.

The tracker should allow multiple simultaneous activities. If an agent
launches two commands in different directories, both locations should
appear as active. Completed activities should remain in a timeline.

8. PROPOSED DATA FLOW

Agent runtime and tool events ----+
                                 |
                                 v
                          Activity model
                                 ^
                                 |
Filesystem/process observations -+

Activity model -> Current agent state -> Filesystem map and activity timeline

Agent events would supply command starts, tool calls, results, and session
state where available. Filesystem and process observations would provide
additional evidence and keep the map current.

9. OPEN DECISIONS

- Which agent runtime should the first prototype track?
- What integration will provide its activity and session events?
- What interface should display the map and activity timeline?
- How should the filesystem map be stored and updated?
- What directories and files should be included by default?

The next proposed design decision is selecting the first agent runtime,
because this determines how command starts, tool calls, results, and
session state can be obtained.

The project remains in the planning stage. No tracker implementation has
been selected or built during this discussion.
